 OpenID Connect Token Hash Algorithm Implementer's Guide 1.0 - draft 00
                openid-connect-token-hash-algorithms-1_0

Abstract

   This OpenID Connect Token Hash Algorithm Implementer's Guide 1.0
   identifies the hash algorithms to use when calculating OpenID Connect
   ID Token hash claims, such as at_hash and c_hash, Financial-grade API
   s_hash, and profile-defined token hash claims, for JWS algorithms
   whose hash function is not completely determined by the algorithm
   identifier in JSON Web Algorithms (JWA) [JWA].

   This guide records implementation guidance for existing and
   registered JWS algorithm identifiers.  It is intended to remain open
   for maintenance and is not intended to advance to Final Specification
   status.

1.  Introduction

   OpenID Connect Core 1.0 [OpenID.Core] defines ID Token hash claims
   such as at_hash and c_hash as the base64url encoding of the left-most
   half of the hash of the ASCII representation of the value being bound
   to the ID Token.  Core says that the hash algorithm is the hash
   algorithm specified in JWA [JWA] for the alg Header Parameter of the
   ID Token's JOSE Header.

   Other OpenID specifications use the same construction.
   Financial-grade API Security Profile 1.0 - Part 2: Advanced
   [OpenID.FAPI.Advanced] defines s_hash for the state value.  OpenID

   Connect CIBA Core 1.0 [OpenID.CIBA] uses at_hash in Push mode and
   applies the same method to Refresh Token hash values using the
   urn:openid:params:jwt:claim:rt_hash claim.

   That rule is clear for algorithms such as RS256, ES384, and HS512,
   because their registered algorithm identifiers specify the hash
   algorithm directly.  It is ambiguous for polymorphic algorithms such
   as EdDSA, because the hash algorithm depends on the EdDSA parameter
   set of the key used to validate the ID Token.  Fully-specified
   algorithm identifiers, such as Ed25519 and Ed448, remove this
   ambiguity.

   This guide clarifies the hash algorithm selection for current JWS
   algorithms used with OpenID Connect ID Tokens.  It does not define
   new JWS algorithms, new ID Token claims, or new ID Token validation
   procedures.

1.1.  Requirements Notation and Conventions

   The key words "MUST", "MUST NOT", "REQUIRED", "SHALL", "SHALL NOT",
   "SHOULD", "SHOULD NOT", "RECOMMENDED", "NOT RECOMMENDED", "MAY", and
   "OPTIONAL" in this document are to be interpreted as described in RFC
   2119 [RFC2119].

   In the .txt version of this specification, values are quoted to
   indicate that they are to be taken literally.  When using these
   values in protocol messages, the quotes MUST NOT be used as part of
   the value.  In the HTML version of this specification, values to be
   taken literally are indicated by the use of this fixed-width font.

1.2.  Terminology

   This specification uses the terms defined by OpenID Connect Core 1.0
   [OpenID.Core], JSON Web Token (JWT) [JWT], and JSON Web Signature
   (JWS) [JWS].

2.  Hash Claim Calculation

   To calculate an ID Token hash claim, such as at_hash, c_hash, s_hash,
   urn:openid:params:jwt:claim:rt_hash, or any other OpenID Connect
   claim that uses the same construction, implementations MUST:

   1.  Select the digest function and, when applicable, its output
       length using Table 1.

   2.  Apply the digest function to the octets of the ASCII
       representation of the value being bound to the ID Token.

   3.  Take the left-most half of the resulting digest output.

   4.  Base64url-encode that left-most half without padding.

   For extendable-output functions, the "resulting digest output" is the
   fixed-length output identified in Table 1.  For instance, SHAKE256
   with 114 bytes of output produces a 114-byte digest output, whose
   left-most half is 57 bytes.

   When EdDSA is used, implementations MUST determine the EdDSA
   parameter set from the key used to validate the ID Token signature,
   such as the JWK crv value, and then use the corresponding entry in
   Table 1.  The EdDSA algorithm identifier is deprecated by [RFC9864],
   and new deployments SHOULD use the fully-specified Ed25519 and Ed448
   algorithm identifiers instead.

   The algorithm identifiers in Table 1 are defined by [JWA], [RFC8037],
   [RFC8812], [RFC9864], [RFC9964], and [I-D.ietf-cose-sphincs-plus].
   The EdDSA parameter sets are defined by [RFC8032].  The ML-DSA
   algorithms use the signing procedure defined by [FIPS204].  The SLH-
   DSA algorithms use parameter sets defined by [FIPS205].  The listed
   SLH-DSA rows are included to track current JOSE algorithm identifier
   registrations; this guide records a recommended resolution but leaves
   final selection of their hash claim digest functions and output
   lengths to the Working Group.

   The SLH-DSA recommendation intentionally uses the public hash or
   extendable-output function family named by the JWS algorithm, rather
   than the SLH-DSA H_msg construction.  [FIPS205] defines H_msg for
   SHA2 Category 1 parameter sets using MGF1-SHA-256 over values that
   include signature randomness and public-key material.  Those inputs
   are not part of the OpenID Connect hash claim construction.

4.  Security Considerations

   This guide does not change the security properties of the ID Token
   hash claims defined by OpenID Connect Core.  It clarifies which hash
   or extendable-output function to use so that OpenID Providers and
   Relying Parties produce the same values.

   For extendable-output functions, implementations MUST use the output
   length specified in Table 1 before taking the left-most half of the
   output.  Using a different output length will produce different hash
   claim values.

   For JWS algorithms whose row in Table 1 marks the claim digest
   function as to be determined, the listed recommendation is
   provisional implementation guidance rather than a final Working Group
   decision.  Implementations using a different rule will produce
   different hash claim values.

   For EdDSA, implementations MUST NOT infer the hash algorithm from the
   alg Header Parameter alone.  They need the EdDSA parameter set of the
   key used to validate the ID Token signature.
